## 0. 검토를 요청하는 이유 (의뢰 시 그대로 전달)

이 서비스는 법원 경매 물건 정보를 모아 보여주고, 등기부·법원 서류에서 뽑은 **권리관계를 규칙
기반으로 정리해** 사용자에게 제시한다. 우리는 변호사·법무사·공인중개사가 아니며 유료 법률자문을
제공하지 않는다.

따라서 다음 두 가지를 확인받고자 한다.

1. **변호사법 §109(무자격자의 법률사무 취급) 저촉 여부** — 등기부상 권리를 "인수/말소"로 분류해
   보여주는 행위, 인수 보증금액을 계산해 보여주는 행위가 법률사무의 취급에 해당하는지.
   프로젝트 내부 결정(`decision-log.md` D-011)으로 **판단·권유·추천 표현을 전면 금지**하고
   사실 서술과 규칙 ID만 노출하도록 개발했으나, 이 선이 충분한지 확인이 필요하다.
2. **면책 문구의 위치·표현이 충분한지** — 현재 면책 문구는 §2-A-6 한 곳뿐이다.

추가로 §5는 법률 리스크가 있다고 자체 판단한 항목이다. 1건(웹의 "예시 데이터" 고지 누락)은
개발 측에서 이미 조치했고, **미해결 1건(면책 문구가 1개 화면에만 있음)** 은 우선 검토를 요청한다.

## 1. 자체 통제 장치 (이미 적용된 것)

- **금지 표현 전수 검사 테스트**가 CI에 있다 — 권리분석 엔진 출력 JSON 전수에서
  `추천 / 안전 / 위험 / 판단 / 권유 / 입찰하세요 / 하지 마세요 / 피하세요`가 0건이어야 통과한다
  (`apps/api/src/rights-analysis/service/rights-analysis.service.spec.ts`).
- **권리분석 엔진 자체는 한국어 문장을 만들지 않는다.** 구조화된 코드(`ASSUMED` /
  `EXTINGUISHED` / `NEEDS_REVIEW`)와 금액·날짜만 내보내고, 한국어 라벨은 화면이 붙인다.
  즉 **검토 대상 문구는 전부 아래 §2~§4에 있다.**
- 모든 판정에 **규칙 ID와 룰 버전**을 함께 노출한다(예: `규칙: RIGHT_CLASSIFICATION v1`).

### E. 매수인 부담 구분 (2026-08-11 추가 — §5-3으로 우선 검토 요청)

섹션 제목 `이 금액에 무엇이 들어갔나`. 사용자가 "경매개시 전에 설정된 근저당도 내가 계산해야
하는지"를 화면만 보고 판단할 수 없다는 문제 때문에 추가했다. 등기부 연동 전이라 **이 물건의
권리 목록이 아니라 권리 종류별 규칙**만 제시한다. 문구는 `notice-labels.ts`의
`REGISTERED_BURDEN_RULES` / `REGISTERED_BURDEN_NOTE`에 있고 웹·앱이 같은 값을 쓴다.

| # | 대상 | 상태 표기 | 설명 문구 |
|---|---|---|---|
| E-1 | `대항력 있는 임차인 보증금` | `인수` | `위 인수 금액에 들어가 있어요. 대항력이 말소기준보다 빠른 임차인만 해당돼요.` |
| E-2 | `근저당·저당권, 압류·가압류, 담보가등기, 경매개시결정` | `인수 안 함` | `매각으로 소멸해서 매수인이 인수하지 않아요. 경매개시 전에 설정됐거나 말소기준보다 앞서도 마찬가지예요.` |
| E-3 | `전세권·지상권·지역권, 등기된 임차권` | `확인 필요` | `말소기준보다 앞서면 매수인이 인수할 수 있어요. 법원이 명세서에 적은 내용은 아래 명세서 기재사항에 나와요.` |
| E-4 | 각주 | — | `이 구분은 권리 종류에 따른 규칙이에요 — 이 물건의 등기부를 확인한 결과가 아니에요. (규칙: RIGHT_CLASSIFICATION v1)` |

**E-2가 이 문서에서 가장 강한 단정이다.** 소제주의(담보물권·압류 계열은 매각으로 소멸)를
근거로 "인수하지 않는다"고 사실 서술했다. 근거 규칙은 `right-classification.ts`의
`ALWAYS_EXTINGUISHED_ON_SALE`이며 §2-C-5 각주와 같은 내용이다. 이 단정의 표현 수준이
적정한지, 예외(특별매각조건 등)를 함께 적어야 하는지 확인이 필요하다.

### F. 목록·지도 카드의 인수 보증금 배지 (2026-08-11 추가)

웹 `/items` 목록 카드 · 지도 마커 호버 카드 · 앱 목록 카드 · 앱 지도 미리보기 시트 · 관심 물건 목록.
가격과 유찰만 보이던 카드에 인수 보증금을 함께 올렸다 — 상세 화면에 들어가야만 대항력 있는
임차인의 존재를 알 수 있어 가격만 보고 판단하는 경로가 열려 있었다. 문구는
`notice-labels.ts`의 `assumedDepositCardLabel`이 만들고 웹·앱이 같은 함수를 쓴다.

| # | 상태 | 문구 |
|---|---|---|
| F-1 | 전액 인수 확정 | `보증금 인수 {금액}` (예: `보증금 인수 5,000만원`) |
| F-2 | 확정분 + 미상 혼재 | `보증금 인수 {금액} 이상` |
| F-3 | 전원 금액 미상 | `인수 금액 확인 필요` |
| F-4 | 인수 0원 확정 | `보증금 인수 없음` |
| F-5 | 명세서 미확인 | `명세서 미확인` (웹·앱 목록 카드) / 배지 없음 (지도 카드는 기존 `매각물건명세서 미확인`을 씀) |

**F-4가 검토 대상이다** — "없음"이라는 단정이다. F-5와 색·문구를 다르게 둬서 "확인 못 함"이
"없음"으로 읽히지 않게 했고, 값의 정의는 상세 화면 헤드라인(§2-D)과 같은 함수를 쓴다.
목록에서 이 숫자를 보여주는 것 자체의 적정성도 §2-D와 함께 확인 요청한다.

   화면(§4)에는 면책 문구가 없다. 스크롤 없이 보이는 위치인지, 3화면 전부에 필요한지 검토 요청.

3. **"근저당·압류는 매수인이 인수하지 않아요"라는 법적 효과 단정** (§2-E-2, 2026-08-11 추가).
   소제주의에 근거한 사실 서술로 작성했고 판단·권유어는 없지만, **개별 물건에 대한 권리관계
   설명이 아니라 권리 종류별 일반 규칙**이라는 점이 문구에서 충분히 드러나는지(§2-E-4 각주),
   그리고 특별매각조건 같은 예외를 함께 적어야 하는지 확인 요청. 이 문구를 넣은 이유는
   사용자가 화면만으로는 "무엇이 내 부담인지"를 판단할 수 없어 오히려 오판 위험이 컸기 때문이다.
