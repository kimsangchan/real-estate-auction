# catch-up — 프로젝트 진행 상황 브리핑

## 1. 수집 (병렬 실행)

```bash
git log --oneline -25
git status --short && git branch --show-current
grep -m1 -H "^- 상태:" docs/work-orders/*.md
```

미커밋 변경이 있으면 `git diff --stat`으로 규모까지 확인한다.

## 2. 교차 검증 (중요)

work order의 `상태:` 라인은 갱신이 누락되곤 한다. **문서 상태를 그대로 믿지 말고 git 로그와 대조할 것.**

- 커밋 메시지의 WP 번호·기능 코드(F-NN)·scope(web/mobile/api/collector)로 실제 진행 여부를 판별한다.
- 문서는 "대기"인데 관련 커밋이 있으면 → 상태를 "진행 중(문서 미갱신)"으로 보고하고 불일치를 명시한다.
- 문서에 "완료"로 명시된 것만 완료로 표기한다.

## 3. 출력 형식 (한국어 브리핑)

1. **한 줄 현황** — 프로젝트가 어디까지 왔는지 한 문장.
2. **WP 상태표** — `WP | 제목 | 문서 상태 | git 근거` 테이블. 문서·git 불일치는 눈에 띄게 표시.
3. **최근 작업 요약** — 마지막 작업들을 주제별로 묶어 3~5줄 (커밋 나열 금지).
4. **미커밋 변경** — 있으면 파일 수와 성격, 없으면 "작업 트리 깨끗함".
5. **다음 작업 후보** — 미완 WP 중에서 구분해 제시:
   - 바로 착수 가능한 것 (선행 조건 해소됨)
   - 사용자 액션이 필요한 것 (각 WP 문서의 §0 섹션 — 예: NCP 콘솔 URL 등록)

## 규칙

- work order 파일 전체를 읽지 말 것 — 상태 라인이 부족할 때만 해당 문서의 §0(사용자 액션)·선행 조건 부분을 추가 확인.
- 브리핑까지만 하고 멈출 것. 다음 작업은 사용자가 고르면 그때 해당 WP 문서 전체를 읽고 착수한다.
- 문서 미갱신 불일치를 발견하면 상태 라인 갱신을 제안한다 (임의 수정 금지).
